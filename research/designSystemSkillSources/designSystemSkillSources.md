## Base UI required references

When wrapping Base UI primitives, require these sources before implementation:

- [Composition](https://base-ui.com/react/handbook/composition): element and callback render props, nested composition, ref forwarding, prop spreading, and the warning about changing default elements.
- [Styling](https://base-ui.com/react/handbook/styling.md): `className` and `style` as static values or state callbacks, data attributes, and CSS variables.
- [useRender](https://base-ui.com/react/utils/use-render.md): implementation, public/internal prop types, state propagation, automatic state attributes, merged refs, and polymorphism.
- [mergeProps](https://base-ui.com/react/utils/merge-props.md): precedence for events, `className`, `style`, refs, and `preventBaseUIHandler()`.
- [Accessibility](https://base-ui.com/react/overview/accessibility.md): Base UI behavioral accessibility versus developer-owned labels, focus, contrast, semantics, and testing.
- [Component API reference](https://base-ui.com/llms.txt): authoritative props, state attributes, CSS variables, default element, roles, and ARIA structure for the exact part being wrapped.

### Wrapper rules

- Preserve the Base UI `render` prop; do not replace it with `asChild`.
- Custom render components must accept forwarded refs and spread every received prop onto the underlying DOM element.
- Render props may be nested; do not swallow props or refs at any layer.
- Preserve static and callback forms of `className` and `style`.
- Use documented state attributes for CSS state styling; do not duplicate or rename primitive state attributes.
- Use `useRender` when a custom primitive needs the same render-prop contract.
- Use `mergeProps` instead of object spread when combining behavioral props.

### Compound component rules

- Read the API reference for the root and every exposed part.
- Wrap parts individually and preserve their prop surfaces.
- Keep Root ownership of controlled/uncontrolled state and forward change-event details.
- Preserve required structural parts such as portals, positioners, popups, triggers, labels, and controls.
- Do not reimplement primitive keyboard navigation, focus management, dismissal, ARIA relationships, or selection state.

### Accessibility ownership

Base UI owns ARIA, roles, pointer interaction, keyboard navigation, focus management, and relationships generated by correctly composed parts. Wrappers own preserving those generated props, refs, event handlers, semantic defaults, and required part structure.

The design system and application still own:

- accessible names and descriptions;
- visible `:focus` / `:focus-visible` styling;
- color contrast;
- semantically valid rendered elements and prevention of invalid nested interactive elements;
- retesting keyboard, pointer, focus, and screen-reader behavior after composition or polymorphism.

## Polar Orbit constraints

Polar Orbit's goal is to make off-brand decisions hard to express in code and impossible to pass CI.

- Typed props accept tokens, not unrestricted CSS values. A typo should be a type error, not a visual regression.
- Remove raw layout elements as authoring surfaces; use polymorphic `Box as="nav"`, `Box as="ul"`, `Box as="li"` instead.
- `as` is a closed set of allowed elements.
- Name tokens by intent, not value: e.g. `background-card`, `text-secondary`, `padding="l"`.
- Do not expose `className`, inline `style`, or arbitrary values as component escape hatches.
- Audit remaining escape hatches through `eslint-disable` usage; growth in exceptions is a design-system bug.
- Encode rules that matter as ESLint checks in CI, not as documentation or prompts.

### Inference

- Optimize for a small, discoverable set of valid constructions, not broad APIs with good documentation.
- Type safety and linting cover complementary boundaries: types constrain token values and element props; lint rules prevent bypass through raw elements.
- Semantic tokens improve future refactoring because intent remains queryable at call sites.

### Qualifications

Polar presents Orbit as an early direction, not a verdict. Closed token sets are still too small for some real interfaces, and the boundary for legitimate escape hatches will continue to move.

## shadcn-cssinjs practical rules

shadcn-cssinjs replaces Tailwind with StyleX while keeping shadcn registry conventions.

### File structure

- Place components under `components/ui/<name>/` with `<name>.tsx` and `<name>.stylex.ts`.
- Keep compound parts together in one module.
- Export registry items as `registry:ui`; shared tokens as `registry:lib`.

### Base UI wrapping

- Namespace primitive imports: `import { Dialog as DialogPrimitive } from "@base-ui/react/dialog"`.
- Forward thin parts almost unchanged and add a stable `data-slot`.
- Styled parts destructure `className`/`style`, compute StyleX output, merge caller escape hatches, and spread remaining primitive props.
- Use Base UI state callbacks for state and transition styling instead of Tailwind `data-state`, group, or peer selectors.
- Use Base UI `render` for polymorphism; do not add `asChild` or `as`.

### StyleX and tokens

- Style modules import `* as stylex` and shared tokens from `../tokens.stylex`.
- Export `styles = stylex.create({...})` with semantic rule names: `base`, `focusable`, `default`, `sizeSm`, `rootChecked`, `popupHidden`.
- Define colors and radii as `stylex.defineVars()` referencing semantic CSS custom properties (`var(--background)`, `var(--primary)`, `var(--radius)`).
- Pseudo-classes, media queries, and transitions live inside StyleX values.
- Use `x()` for StyleX composition; use `cx()` only to append external class names; merge caller inline styles after StyleX's returned `style`.

### Props and refs

- Derive public props from the intrinsic element or exact Base UI part.
- Omit only properties the wrapper must narrow or own.
- In React 19, refs pass through `React.ComponentProps` and `...props`; do not add `forwardRef` by habit.
- Avoid destructuring away `ref`.

### Retained from shadcn

- Registry-first distribution, `registry.json`, `registryDependencies`, generated `/r/*.json` payloads.
- Semantic CSS variable names, `.dark` class theming, OKLCH-compatible values, `--radius`.
- Familiar component names, variants, sizes, compound exports, Lucide icons, `data-slot`.

### Replaced

- Tailwind utility strings in registry implementations.
- `cn()` / `tailwind-merge` as the primary style mechanism.
- CVA for variants; use typed StyleX rule records.
- Radix primitives and `asChild`; use Base UI primitives and `render`/`useRender`.
- Tailwind `group-*`, `peer-*`, arbitrary data-state selectors, and responsive prefixes.

### Practical checklist

1. One component per folder: `<name>.tsx` + `<name>.stylex.ts`.
2. Derive props from the exact element or Base UI part.
3. Let React 19 refs pass through props.
4. Wrap interactive behavior with Base UI; use intrinsic HTML when no primitive behavior is needed.
5. Put styles in `stylex.create()`; put colors/radii behind `stylex.defineVars()`.
6. Use `x()` for StyleX composition; merge caller `className` with `cx()` and caller `style` after StyleX.
7. Use Base UI `className={(state) => ...}` for state and transition styling.
8. Use Base UI `render` for polymorphism.
9. Preserve shadcn registry metadata, semantic tokens, variants, and `data-slot`; do not preserve Tailwind-specific implementation techniques.
